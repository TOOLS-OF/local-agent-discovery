# Shared dogfooded repositories

Apply this policy to every repository the user owns or contributes to and also uses as local tooling, regardless of organization, language, package manager, harness, or machine.

- Distinguish the shared runtime installation, the integration checkout, and each contributor's development worktree. Discover and record the remote, default branch, installed command paths, exact revisions, and existing worktrees before changing them.
- Each agent or contributor works on its own named branch in its own worktree. Prefer `<agent>/<purpose>` names. Do not switch another contributor's checkout, reset their changes, reuse their branch, or point a global command at a mutable development worktree. Pass these instructions explicitly to workers that do not inherit global instructions.
- Exercise development versions through explicit local entrypoints or isolated package prefixes. Install and test the complete dependency closure, including sibling shared libraries. A successful source invocation alone does not prove a packaged installation works.
- Keep one canonical default installation per machine and command. Make PATH precedence explicit; identify duplicate wrappers and stale links. A global command must not silently change when a contributor edits, moves, or removes a worktree.
- Promote the best validated integrated revision through the repository's established review and release process. "Best" means the most recent compatible integrated revision whose required tests, packaging checks, and representative local workflows pass; it does not mean the newest unmerged branch. Track useful unmerged work so it can be reconciled rather than lost.
- Serialize promotion per repository and machine. Stage an immutable, revision-identified installation, test its installed entrypoints and dependencies, record the previous working version, then switch the default using the platform's supported replacement mechanism. If a required check fails, retain the working default and record the blocker. Routine validation and reversible local promotion within the user's request need no additional confirmation.
- Maintain a machine-local registry with remote URL, integration branch and commit, installed commit, package and runtime versions, installation location, resolved command paths, validation evidence, prior version, promotion date, and owner. Record missing installations and version drift rather than claiming the machine is current. Recheck on contribution and before relying on a tool; schedule checks only when requested.
- Preserve dirty files, untracked assets, worktree metadata, and unpushed commits during relocation. Audit absolute `.git` pointers, common Git directories, junctions, symlinks, wrappers, and configuration paths before use on a new drive. Repair copies after recording the original mappings; do not rewrite the sole recovery source.
- Scope completion claims precisely: code reviewed, merged, installed, validated, and available on PATH are separate states. Update the registry after promotion and report any remaining gap. Do not invent remote publication, review, merge, or scheduler authorization.

These instructions define a workflow; they do not create an automatic updater. Keep this policy consistent across user-level harness instructions and include it in repository onboarding where the user requests that rollout.
